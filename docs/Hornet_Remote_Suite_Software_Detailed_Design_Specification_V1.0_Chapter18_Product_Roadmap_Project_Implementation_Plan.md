# Hornet Remote Suite 软件详细设计说明书 V1.0
## 第18章 产品路线图与实施计划

修订日期：2026-09-24。实施目标是统一 Power Suite 类桌面套件。原计划先做 IDE/AI、长期不包含 X11/打印，无法达到该目标，现调整如下。

## 18.1 阶段与退出条件

| 阶段 | 交付物 | 前置依赖 | 退出门槛 |
|---|---|---|---|
| M0 技术验证 | 统一模型/API原型、X Server适配、RDP帧桥、VNC bridge、LPD到打印机闭环 | 无 | 原生引擎版本/分发材料明确；DPI/输入/隔离PoC通过；形成选型ADR |
| M1 基础工作台0.x | 主机/凭据/布局、SSH终端、SFTP、任务与恢复、安装包 | M0共同契约 | 第12章M1全部通过，不能标完整套件 |
| M2 套件V1.0候选 | 增强终端/FTP、X11与LAN XDMCP、内嵌RDP/VNC、LPD打印中心 | M1；M0图形与打印门槛 | 四类核心用途均可在统一工作台完成；M2用例和安装包验收通过 |
| M3 高级兼容 | 第24章认证、终端、X扩展、打印格式等兼容包 | M2 | 每个C-*项有结果和证据；明确差异保留在发布说明 |
| M4 增量平台 | IDE、Git、插件、AI、企业管理 | 核心套件稳定、独立需求与安全设计 | 扩展自己的验收通过，不使核心依赖云服务 |

M3 是完整对标工作的一部分，不能用 M2 已支持四类用途宣称逐功能等价。安全上明确排除的遗留能力始终列出，不隐藏差异。

## 18.3 估算方法

原章节“5天/7天”仅为未经估算的占位，统一废止为承诺排期。M0 输出实际原型结果后，按人员能力、引擎维护量、测试矩阵和分发工作给出乐观/基准/风险三档人周。

至少需要桌面/前端、Node/协议、Native/Windows图形打印、测试与发布四类能力；可由少人数兼任，但不能把并行团队的人周直接当作单人日历工期。未确定团队和预算，不给出固定6个月或五年承诺。

## 18.4 首个可开发迭代

1. 建立 packages/contracts、配置库和凭据服务接口，确定 profileId/connectionId/leaseId。
2. 完成一个主机打开终端和文件、共享SSH、关闭终端不断传输的垂直闭环。
3. 加入 known_hosts、断线恢复、传输检查点和安装包测试。
4. 在独立 PoC 中验证图形与打印风险，结果回写21—23章及 ADR。
5. 按M2门槛合入工作台，不以外部启动器替代集成验收。

## 18.5 风险和决策触发

- X/RDP引擎嵌入、字体或GLX不符合目标应用：更换适配或公开限制，不能推迟验证到发布前。
- 认证扩展与ssh2能力不一致：在M0/M3做独立认证适配；无法验证则标partial。
- 打印提交崩溃结果未知：按unknown处理，不以自动重试提升表面成功率。
- 平台矩阵超出团队能力：先交付已测Windows矩阵，其他平台按功能开放。
- IDE/AI扩张挤占核心：分别立项，不移动M2的图形与打印验收。

## 18.6 变更控制

每个新增功能对应需求ID、责任模块、契约、错误处理及测试。改变协议/持久化模型时同时更新第1、4、11、12和24章。发布兼容范围必须由实测报告支撑。
